# Glossary

Domain terms that appear in code, commit messages, and other docs. Add a term when you introduce it; don't let new vocabulary land unexplained.

---

**Account** — A row in the `accounts` table. Either a real account (`bank`, `credit_card`, `investment`, `asset`, `liability`, `loan`) **or** a budgeting category (`account_type='category'`, with `category_kind` distinguishing income vs expense). Categories are accounts in the unified data model. See [decisions/0002-unified-accounts-table.md](decisions/0002-unified-accounts-table.md) and [decisions/0017-account-discriminator.md](decisions/0017-account-discriminator.md).

**ADR** — Architecture Decision Record. A short markdown file under `docs/decisions/` capturing the context, decision, and consequences of a material design choice at the time it was made.

**Merge** — Folding a duplicate row into the one that survives: the loser keeps `is_merged_into` pointing at the survivor, which carries `is_merge_winner`. Always user-driven — the editor offers merge candidates and the user picks. There is no auto-merge and no confidence-scored pipeline; the `merge_rules` table reserved for one was dropped by migration 044.

**Balance after** — `txn_header_account_balances.balance_after`: the running account balance on a given account after a given header is applied. One row per `(header, account)`. Migration 090 drove this from triggers; **migration 102 dropped that family**, and it is now recomputed from application code — an EF `SaveChangesInterceptor` (`LegDerivedRecomputeInterceptor`) scans the change tracker and calls the Postgres walk. The only triggers left in the schema are the two `txn_headers` immutability guards. Read-side surfaces it through `resolved_transactions.balance_after`.

**Category** — Moneydance vocabulary for what is implemented here as `accounts.account_type='category'`, with `category_kind` ∈ {`income`, `expense`, `adjustment`} naming the flow direction. Categories support a `parent_id` hierarchy (a category may have child sub-categories, its own direct transactions, or both); other account types do not.

**`category_kind`** — The flow-direction discriminator on category rows: `income`, `expense`, or `adjustment`. Required when `account_type='category'`, NULL otherwise. **`adjustment`** was added by migration 224 for entries that are neither earned nor spent: a revaluation booked as an expense is netted into that period's spending and can drive the total negative, and booked against income it can do the same to income. Separated from `account_type` because *what kind of thing this row is* and *which flow direction* are orthogonal concepts (per [decisions/0017-account-discriminator.md](decisions/0017-account-discriminator.md)).

**Loan** — `account_type='loan'`. Distinct from `liability` because loans carry amortization metadata (APR, term, compounding, face value) in `loan_terms` (migration 127) and appear in their own UI section. Amortization shipped: ADR-0050 covers the account editor and schedule, ADR-0078 the managed loan-payment reminder whose principal / interest / escrow split is computed live per occurrence.

**Counterparty** — The other side of a flow. Pairing is STRUCTURAL, not a stored link: the two legs of a posting share a `txn_legs.posting_index` under one `txn_headers` row, so there is no denormalised `counterparty_id` to keep in sync and no symmetry trigger (both belonged to the pre-ADR-0022 `transactions` table, dropped by migration 025). See [decisions/0022-txn-headers-and-legs.md](decisions/0022-txn-headers-and-legs.md).

**Cursor pagination** — Register reads use a composite cursor instead of `OFFSET`, so the index range scan is bounded by the cursor rather than the offset and stays fast however deep into the history the page sits. The cursor is `(posted_at, header_seq, entry_key)` — `seq` replaced `created_at` as the tiebreaker in migration 097, and the entry key is the header id on the owning side (the originating account, or the event's investment side) and the leg id on every other side, a one-split's other side included (stored as `txn_legs.notes_groups_by_header`). Sort column and direction are parameters of the register's keyset query (`RegisterQuery`), not fixed to date-descending.

**Double-entry / symmetric postings** — One user-facing event is a `txn_headers` row; its money movements are `txn_legs` rows paired by `posting_index`, each pair summing to zero, except a transfer between real accounts in different currencies, whose two legs each hold their own account's amount ([decisions/0114-benchmarks-and-currency-conversion.md](decisions/0114-benchmarks-and-currency-conversion.md) D13). There are no `splits` or `inv_txn_securities` tables — security metadata (security_id, quantity, unit_price) lives on the holdings-side leg of each pair. See [decisions/0022-txn-headers-and-legs.md](decisions/0022-txn-headers-and-legs.md).

**External ID** — A feed-supplied identifier (`txn_headers.external_id`) used as the idempotency key during sync upserts, unique per `(ledger_id, external_id)`. `ck_txn_headers_external_id_for_non_manual` requires one on every non-manual row, so CSV imports — which have no issuer-assigned id — emit a deliberately non-matching unique value rather than omitting it.

**Feed** — A bank/brokerage data source. Currently SimpleFIN (chosen) and Plaid (rejected). Manual import counts as a degenerate feed.

**Folder** — A named grouping of real accounts in the sidebar, a row in `account_folders` (migration 258, [decisions/0106-folders-replace-tabs.md](decisions/0106-folders-replace-tabs.md)). Shared by everyone on the ledger, one account type each, nested to any depth; an account sits in at most one (`account_folder_members`). Not an account: it holds no transactions, and its total is the sum of the accounts under it. The account pickers, the Accounts tab of Structure and the dashboard do not show folders. It replaced the per-user sidebar tabs. Not to be confused with a parent category, which is `accounts.parent_id`.

**Gain incl. income** — The first row of the Overview's Investments return: `gain` from `GET /reports/returns` (and MCP `returns`), exactly `endValue − startValue − netContributions` for the window. It is the change in value that contributions and withdrawals do not explain: price movement, realized or not, plus dividends and interest, less fees and investment expenses; not annualized, and for the whole scope, so the per-account rows do not carry it. Measured from the start value, it is neither the FIFO realized gain nor the unrealized gain against cost. Shown in the ledger's reporting currency, converted by the date rules of ADR-0114 D7 and unhedged, and null with `rate_unavailable` when a rate is missing ([decisions/0114-benchmarks-and-currency-conversion.md](decisions/0114-benchmarks-and-currency-conversion.md) D7, D9; it read "mixed" across currencies before, [decisions/0109-overview-is-an-attention-first-home.md](decisions/0109-overview-is-an-attention-first-home.md), 2026-11-03 amendment).

**Inactive account** — `accounts.is_active = false`. Single lifecycle flag (mig 106): the user marked the account deactivated. Default views hide it from pickers and the sidebar; the sidebar's "Show inactive" toggle surfaces it greyed-out with a strikethrough. Mig 106 dropped the prior orthogonal `is_hidden` column and collapsed its rows here; the MD importer maps both MD-side `is_inactive` AND `hide` flags to this column. A new transaction never lands on one: creates and reminder fires refuse an inactive account, and auto-post skips a bank reminder that uses one and names it in its notice. An edit of a transaction or reminder keeps an inactive account it already carries and refuses one newly added.

**Bootstrap token** — A 32-byte random one-shot token minted at API startup when no WebAuthn credentials exist (per ADR-0013). The plaintext is written to the API logs once; the SHA-256 hash lives in `bootstrap_tokens` until consumed by `/api/auth/setup/{token}`. Subsequent registrations require an authenticated session or a recovery code instead.

**Ledger** — A self-contained book of accounts/transactions/etc. (a row in `ledgers`). The unit of book-isolation introduced in Phase A per [decisions/0020-multi-ledger-row-scoped.md](decisions/0020-multi-ledger-row-scoped.md). `ledger_id` is now **denormalised onto every ledger-scoped table** — migrations 071 and 072 did that deliberately, because an RLS policy written as a subquery against an anchor table adds that lookup to every row a recompute reads, which multiplies its cost. Coherence is held by a composite FK to the parent rather than by the subquery. There is no seeded ledger: migration 186 deleted the placeholder `Default` and `Demo` rows (ADR-0088).

**Demo ledger** — A ledger the hub's **Demo ledger** action adds for the caller (`POST /api/ledgers/demo`), named Demo, Demo 2 and so on at the lowest free number; setup creates none. A C# generator (`src/Api/Provisioning/Demo/`) writes a Moneydance export of five years of a made-up household, ending on the day it is added, from a fixed seed and that date, so the same date always gives the same bytes. The export is imported as an upload is, and the same background job's examples phase (`DemoSeeder`) then adds what an export cannot carry, through the app's own writers and their endpoints' checks: folders, investment settings, budget targets, register edits beside the bank's originals, hidden re-sent copies, a half-reconciled statement, a card statement imported through a saved CSV layout with its merges, reminders, saved reports, a Home layout and one snapshot. The phase records itself on the Demo's **Ledger operation** row (provider `demo`, "Demo examples"), and the hub names any example that was not added. Otherwise an ordinary ledger: nothing rebuilds it, and deleting it is deleting a ledger. See [decisions/0115-the-demo-is-generated-imported-and-seeded-from-the-hub.md](decisions/0115-the-demo-is-generated-imported-and-seeded-from-the-hub.md).

**Recovery code** — One of 10 single-use codes minted at WebAuthn registration (ADR-0013). Stored as an Argon2id PHC string in `recovery_codes`; one code is good for one re-registration of a fresh credential when every authenticator has been lost. Regeneration invalidates all prior codes.

**Synthetic ledger** — The atomic per-test arrange step used by integration tests. Each test calls `SyntheticLedger.CreateAsync` to mint a fresh ledger + user + owner grant in one transaction; the test then seeds further state under those ids, on the test's own database (a clone of the migrated template). No real-export data. See [engineering-standards.md §5.2](engineering-standards.md#52-every-integration-test-gets-a-database-of-its-own).

**`user_ledger_grant`** — A row in `user_ledger_grants` granting a user one of three roles on a ledger: `owner` (read, write, share, delete, and the ledger's bank connections and notification targets), `editor` (read and write, including syncing; not the bank connections or notification targets, which became the owner's in 0.122.0, ADR-0083), or `viewer` (read-only). Every ledger keeps at least one human owner. The API enforces it in a serializable transaction (ADR-0083 D4); no database trigger does (migration 087 dropped it).

**`last_opened_ledger_id`** — `users.last_opened_ledger_id`. The ledger this user most recently switched to. UI auto-opens it on next login after re-validating the user still has a grant. NULL on first login → ledger picker.

**Hidden transaction** — `txn_headers.is_hidden = true`. Soft-deleted from registers and reports; the row remains. Canonical since migration 230 — there is no override layer left to resolve through. A hidden trade is no trade: it values no position and, since migration 273, prices no day ([decisions/0084-trade-derived-security-prices.md](decisions/0084-trade-derived-security-prices.md) D4).

**Holding** — A `(account, security)` rollup row. Aggregates lots into a single position for UI summary purposes. Lives on the **Holdings sibling** account, not the brokerage cash account.

**`share_decimals`** — Per-security precision for share quantities (Moneydance's `dec` field), 0 to 12. The investment mapper looks this up so a raw `samt` is read as `samt / 10^dec` shares — the same integer is ten times fewer shares at `dec=5` than at `dec=4`.

**Minor units** — The number of decimal places a currency's money is counted in: its ISO 4217 exponent, 0, 2 or 3. Every money figure is displayed, typed and stored at its own currency's minor units, read from one checked-in ISO 4217 data file the API and the SPA share; never from the browser's `Intl` defaults, which disagree with ISO for several currencies ([decisions/0114-benchmarks-and-currency-conversion.md](decisions/0114-benchmarks-and-currency-conversion.md) D15). Prices, share quantities and exchange rates are not money and do not follow them. Not to be confused with a quote's minor unit (`GBp`, pence), which is a unit Yahoo quotes in, not a number of places.

**Holdings sibling** — A system-managed `account_type='investment'` row at the root, paired 1-1 with a brokerage account via the brokerage's `holdings_account_id` self-FK. Hosts the holdings-side legs of every investment transaction (buys, sells, dividend reinvests, etc.) so the brokerage account itself stays purely a cash account. `is_system=TRUE` keeps the sibling out of normal account lists. It is in its brokerage's currency: a brokerage's currency edit carries to it, and the consistency check's `holdings_currency` projection reports one that differs (ADR-0019 Rule 4, 2026-11-04 amendment). Originated in [decisions/0019-symmetric-postings.md](decisions/0019-symmetric-postings.md), which ADR-0022 superseded — the current headers+legs model is [decisions/0022-txn-headers-and-legs.md](decisions/0022-txn-headers-and-legs.md).

**Leg** — One row of a paired posting. Every Moneydance split decomposes into two legs (origin + counterparty). `leg_index` is the original MD split index, preserved for ordering inside a `txn_group_id` group. Each leg is one side's: it holds that side's own memo (`leg_memo`) and tags (`txn_leg_tags`), and the stored memo-and-tags presentation of its row (`notes_*`, `txn_leg_note_tags`).

**Lot** — A specific tranche of shares acquired at a known cost basis on a known date. Critical for capital-gains calculation (specific identification, FIFO, etc.).

**MD** — Internal shorthand for Moneydance, the predecessor app. Used in code comments, never in product UI.

**Merge candidate** — A settled row the row being edited could fold into, offered in the editor's "Merge candidates" strip. Picking one folds the edited row into it, and it survives with its own fields. Computed per request, not stored — the `merge_candidates` table was dropped by migration 044.

**Origin** — `txn_headers.origin`. The icon-level source mechanism of a transaction (mig 107, ADR-0035): `manual` (typed), `online_import` (any live feed — SimpleFIN, MD+ Direct Connect, OFX online), `file_import` (any file upload — OFX/QFX, CSV, QIF). Drives the register provenance icon. Per-provider audit detail lives on `provider_key`.

**Originating account** — `txn_headers.originating_account_id` (migration 263). The account a transaction was entered from: the entering side of a one-split, the split side of a multi-split, the brokerage of an investment event. A reshape hands it to the side that makes it: splitting from one side makes that side originating, and setting an action in a brokerage register makes the brokerage originating. An ingested row belongs to the account it was imported into, and a Moneydance row to its Moneydance home account. Migration 263 filled it for existing transactions from their shape. Not to be confused with **Origin**, the ingest mechanism.

**Own / inherited** — A side's own memo and tags are stored on its own leg. A side with none of its own shows the other side's, inherited: on a one-split the other leg's, and on a split line seen from its opposite side, that line's split-side leg. The register marks an inherited value with a small arrow. Typing a value makes it this side's own and leaves the other side untouched; clearing it inherits again. Blank always means inherit; there is no explicit "none". Decided in [decisions/0108-memo-and-tags-per-side.md](decisions/0108-memo-and-tags-per-side.md).

**Provider key** — `txn_headers.provider_key`. Specific ingest provider that wrote a row: `simplefin`, `mdplus`, `ofx`, `qif`, `csv`, `csv-generic`, `csv-fidelity`. `csv` is what the Moneydance import writes for a row Moneydance's own text import brought in (`md:txtimport`, or an `mdtxtimport:` / `mdcsvimport:` / `mdqifimport:` FITID); a CSV file import in Coffer writes its reader's key, `csv-generic` or `csv-fidelity`, never bare `csv` (`provider_security_mappings` is keyed by the specific provider, so the distinction is load-bearing). NULL when `origin='manual'` (DB CHECK enforces the bi-implication). Drives the per-provider hover label on the register provenance icon AND is the per-provider dedup scope in `IngestOrchestrator`.

**Merge winner** — `txn_headers.is_merge_winner = TRUE`. A row that another row was merged into (the loser carries `is_merged_into` pointing at this row's id; the loser is hidden from the register). Maintained atomically with `is_merged_into` in `TransactionsRepository.PatchAsync`. No surface undoes a merge; deleting a winner un-merges its losers (`is_merged_into` is `ON DELETE SET NULL`), which return to their registers, and the delete recomputes their balances, positions and trade days. Renders as a small overlay on the register's provenance icon. See ADR-0035.

**Original** (formerly *override*) — The FEED's values for a header, kept in `txn_header_originals`. ADR-0100 and migration 230 inverted the old arrangement: the canonical `txn_headers` row now holds the CURRENT values and the sidecar holds what the feed sent (payee, memo, dates, check number, and since ADR-0114 D15 the transaction's amount with a rounded-at-import flag), captured once on the first edit, seeded by the Moneydance import where MD kept a feed payee or memo that differs from the curated one (ADR-0100, 2026-10-21 amendment), or seeded by an import that rounds an amount to its currency's places, keeping the bank's figure as sent; a promote-on-clear restates that amount (ADR-0100, 2026-11-16 amendment). The old direction — an immutable feed row plus an overlay — could not represent a field being CLEARED, so a payee could never be emptied. `resolved_transactions.has_overrides` is simply "an original is on file", which for a Moneydance row is not the same as "edited in Coffer"; it is no longer on the register API response, which nothing read it from.

**Pending transaction** — A feed-supplied row not yet settled, flagged by `txn_headers.is_pending`. There is no separate holding table: `pending_transactions` was dropped by migration 044, and a pending row lives in `txn_headers` like any other.

**Perspective** — What a filter, a search or a report evaluates a row by: exactly what the register showing it shows, so a filter never matches something the row does not show. A category register filters on its own view of a line; the split-side register filters on the transaction's memo and tags together with each line's own. A report always takes the real account's perspective: a value only a category side shows counts in that category's register and never in a report.

**Register** — The chronological list of transactions for one account. The primary read view of the app.

**Register entry** — One row of a register, keyed by its entry key (see **Cursor pagination**). A transaction is one entry on the side that owns it, each of its lines on another account is an entry there, and a transfer is an entry on each account it touches. Registers page by entries, `GET /transactions/entries` lists them across the ledger for the Overview's To review and Recent transactions, and an account's `needsReviewCount` counts its entries awaiting review. Not a **transaction line**: MCP `list_transactions`, the budget drill and a tag's transactions list one line per leg on the accounts they reach, named by `legId` and in its own `currencyCode`.

**Resolved view** — `resolved_transactions`. The read-side projection over `txn_headers` ⨝ `txn_legs`, plus accounts and securities, and the stored memo-and-tags presentation of the row's leg and of its posting's other leg (`notes_*`, `counterparty_notes_*`). It has no memo or tag column of its own (migration 266); tag names come from `txn_leg_note_tags`. All app/report queries go through this view. It no longer coalesces an overlay — since migration 230 the canonical row is already current.

**Reminder** — Moneydance term for what we call a `recurring_transaction`. Templates that produce future-dated transactions on a schedule.

**Rule** — *Not built.* Pattern-matching on feed payee/memo to auto-categorize at sync time is still an open backlog item; the `transaction_rules` table it was sketched around was dropped by migration 044. What exists instead is similar-payees RECALL: the editor offers the (payee, counterparty) pairs chosen on prior rows from the same feed with the same raw payee, and the user applies one.

**Ledger operation** (formerly *sync run* / *provider run*) — One recorded operation on a ledger: a feed sync (SimpleFIN pull), a file import (OFX, QIF or CSV), a Moneydance bootstrap import, a Demo's examples (provider `demo`, see **Demo ledger**), a quote refresh, or a snapshot restore. Logged in `ledger_operations` (was `sync_runs` → `provider_runs` → `ledger_operations`, migrations 038 → 132 → 185) for audit and the Settings → Activity timeline.

**Side** — One account's view of a transaction: the leg that account carries on each posting, and what its register shows. Memo and tags are per side: a one-split has no transaction-level memo or tags, and each side's leg holds its own (see **Own / inherited**). Only a split and a multi-posting investment event also have a transaction-level memo and tags, on the header.

**Split side / Opposite side** — The two views of a multi-split. The split side is its originating account: its register shows the transaction as one row, with the transaction's memo and tags ("whole transaction") and each line's own; a line with no value of its own shows none, never the transaction's. The opposite side is each line's other account: there every line is its own read-only row, showing the line's value (its own, else inherited from the line's split-side leg), and the transaction-level memo and tags are not in play. A read-only row offers no Edit or Duplicate.

**Stored memo-and-tags presentation** — What the one memo-and-tags rule (`MemoTagRules`) produces for each leg, stored at write time: the `txn_legs.notes_*` columns and `txn_leg_note_tags` (migration 264). `LegNotes` recomputes it in the transaction of every write that changes one of the rule's inputs; every reader (register, filters, search, reports, MCP) reads it instead of evaluating the rule. Derived, never an input, and copied verbatim by a snapshot restore. A change to the rule ships as a numbered recompute step.

**Tag name key** — `tag_name_key(name)` (migration 263): the one definition of "the same tag name", ignoring case and surrounding white space. A ledger holds one tag per key (`uq_tags_name_key_per_ledger`, migration 264); every writer, the Moneydance importer included, resolves a name through it, and the upgrade merged existing case variants into the earliest-created one.

**Trigram** — `pg_trgm` extension; computes similarity between strings as overlap of three-character substrings. Used in payee fuzzy matching.

**Txn group** — A compatibility projection in `resolved_transactions`, not a stored column: the view computes `txn_group_id` as the header id when the header has more than one posting, else NULL. Grouping is structural (shared `header_id`); the UUID survives only because read-side callers were written against it. See [decisions/0022-txn-headers-and-legs.md](decisions/0022-txn-headers-and-legs.md).

**Uncategorized** — A reserved expense account that catches feed splits before the user (or a rule) categorizes them. A system category (`is_system`), one per ledger, created the first time an ingest (a bank feed or a file import) or a Moneydance import needs it; the Moneydance import lands MD's blank-named top-level leaf categories on it, whatever their Moneydance kind (ADR-0027, 2026-10-21 amendment). Drawn as the neutral chip and dot wherever a category is shown, recognised by its system flag, never by its name, which a person's own category may share (ADR-0021 Rule 5, 2026-11-03 amendment). On a report chart, where the neutral is no series colour, it borrows a free colour family as any category does whose own is taken (ADR-0104 D4, 2026-11-06 amendment).

**Host updater** — `app-upgrades.sh` in the install directory: a script the install user's crontab runs every minute (ADR-0110). It reads the upgrade mailbox through a throwaway container and, for a valid request, runs `upgrade.sh` detached. It decides everything itself, since the API can write any well-formed request. Commands: `enable`, `disable`, `status`, `ack`, `set-token`, `probe`, `tick`. Not the API: the API container has no Docker access.

**Upgrade mailbox** — The `coffer_mailbox` volume, mounted at `/app/mailbox`, through which the API and the host updater talk (ADR-0110). A message is an empty file whose name carries it: `req_v1_…` is a request from the app, `st_v1_…` a status the host wrote back, `hb_v1_…` the host's own state. Kept apart from `coffer_data` so the host reads it without seeing the data or the keys.

**Upgrade pin** — A `backup_pins` row of kind `upgrade` (migration 268): the fresh verified backup an upgrade started from the app takes first, labelled "before upgrade X to Y". The newest two are kept and the rest trimmed when an upgrade succeeds; one from an attempt that changed nothing is released at once. Not an admin pin, which never expires. See [decisions/0110-upgrade-from-the-app.md](decisions/0110-upgrade-from-the-app.md).

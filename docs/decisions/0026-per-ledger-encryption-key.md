# 0026 — Per-ledger encryption key (LEK) wrapping app-level secrets

* Status: Accepted
* Date: 2026-05-15
* Refines: [ADR-0014](0014-encryption-at-rest.md)

## Context

[ADR-0014](0014-encryption-at-rest.md) committed Coffer to envelope
encryption for high-value secrets: per-record data encryption key
(DEK), wrapped by a deployment-level key encryption key (KEK)
loaded at API startup. Phase 5 (SimpleFIN sync) is the first
caller — the SimpleFIN access URL is the first secret we need to
store.

Two adjacent requirements pushed us to refine the wrapping shape
before writing the first secret:

1. **Per-ledger backup / export.** A ledger is the unit of
   user-facing book isolation under ADR-0020. SPA-initiated "export
   this ledger" is on the medium-term roadmap; without a per-
   ledger crypto boundary, an exported blob would either need to
   re-encrypt every secret with a separate transfer key (ad-hoc) or
   carry plaintext (unacceptable).

2. **The data model already has a per-ledger boundary.** Per-record
   DEKs are correct when the record is the unit of access; for
   secrets that live and die with a ledger (SimpleFIN URL,
   webhook secret, future per-ledger API tokens) the natural unit
   is the ledger.

## Decision

Insert a **per-ledger encryption key (LEK)** between the deployment
KEK and the per-secret seal:

```
master KEK  ─wrap (AES-GCM)─→  wrapped LEK on the `ledgers` row
       ↓ (loaded from COFFER_MASTER_KEK_BASE64 at startup)
       └─ unwrap → LEK (in-memory only)
                    ↓
                    AES-GCM-seal each secret with the LEK
                    ↓
                    `ciphertext` columns (per-secret)
```

The LEK is 256-bit AES key material generated by
`RandomNumberGenerator.GetBytes(32)` at ledger creation.

### Schema (migration 035)

Three new columns on `ledgers`, all NOT NULL post-backfill:

* `wrapped_lek BYTEA` — `nonce(12) || ciphertext(32) || tag(16)` =
  60 bytes. The AES-GCM ciphertext of the LEK under the master
  KEK referenced by `lek_kek_id`.
* `lek_kek_id TEXT` — identifier for the master KEK that wrapped
  this LEK. Starts at `"v1"`; rotation introduces `"v2"`, etc.
* `lek_created_at TIMESTAMPTZ NOT NULL DEFAULT now()` — audit;
  also drives the rotation cadence ("re-wrap LEKs older than X").

The migration ships the columns as NULLABLE so it can run before
the API has a chance to backfill existing rows. A follow-up
migration sets NOT NULL once backfill is verified complete.

### Algorithms

* **Wrap / unwrap** the LEK: AES-GCM-256 with the master KEK and
  a fresh 12-byte random nonce. Stored as
  `wrapped_lek = nonce || ciphertext || tag`.
* **Seal / open** secrets with the LEK: AES-GCM-256 with the LEK
  and a fresh 12-byte random nonce per call. Each secret column
  stores `nonce || ciphertext || tag`.

AES-KW (RFC 3394) was considered for the wrap step — it's purpose-
built for key wrapping and doesn't need a nonce — but
`System.Security.Cryptography` only ships AES-GCM in-box. Adding
BouncyCastle for one wrap operation isn't worth it; AES-GCM with
a 12-byte random nonce + integrity tag is cryptographically sound
for this size class (we wrap exactly one 32-byte LEK per ledger;
random-nonce collision risk is negligible at that volume).

### Master KEK source

Same options as ADR-0014 §Layer 4. Phase 5 ships with
`COFFER_MASTER_KEK_BASE64` env-var loading (32 bytes base64).
Production deployments **must** set it; dev / CI use a sample
value documented in `.env.example` clearly marked as non-secret.

Failure to load the master KEK at API startup is fatal — the API
refuses to serve. There is no "skip crypto" mode.

### Lifecycle

* **Create ledger** — generate a fresh LEK, wrap, persist alongside
  the new `ledgers` row in the same transaction. Repository's
  ledger-creation path is the only writer.
* **Read secret** — unwrap the LEK (1 AES-GCM op), open the secret
  (1 AES-GCM op). LEK lives in memory only for the duration of the
  request; not cached across requests (negligible cost — single
  AES op).
* **Write secret** — seal with the LEK, persist
  `nonce || ciphertext || tag` to the secret's column.
* **Rotate master KEK** — re-wrap every ledger's LEK with the new
  master KEK, update `lek_kek_id`. Single column update per
  ledger. Background job; live API stays available.
* **Rotate LEK** — re-seal every secret in the ledger with a fresh
  LEK, update `wrapped_lek` + `lek_created_at`. Per-ledger; touches
  only the few secret rows.
* **Lose master KEK** — bank tokens unrecoverable. User re-links
  feeds. Bulk transaction data unaffected. Same blast radius as
  ADR-0014's per-record DEK model.

### Scope

Same discipline as ADR-0014: envelope encryption is for **high-
value secrets only**. Bulk transaction data stays plaintext
(otherwise indexes / queries / reports break, and disk + backup
encryption already cover the realistic threat). Phase 5 callers:

* `feed_connections.access_url_ciphertext` (Phase 5 slice 1).

Anticipated future callers (each will lock the column name when
it lands):

* Webhook signatures for inbound SimpleFIN push events.
* Per-ledger API tokens for third-party export.
* Encrypted per-ledger backup blobs (SPA-initiated export).

## Consequences

**Positive**

* Ledger boundary = crypto boundary; matches ADR-0020's data
  model.
* SPA-initiated per-ledger export becomes one blob:
  `{wrapped_lek, kek_id, sealed_payload}`. Receiver with the same
  master KEK unwraps; receiver without it has authenticated
  ciphertext (no plaintext leak).
* Master-KEK rotation re-wraps one row per ledger (1-10 rows
  typically) instead of one row per secret.
* LEK rotation re-encrypts the small set of secrets in one
  ledger; no impact on bulk data.
* Composes with hardware-backed master KEK (TPM / YubiKey)
  without schema changes.

**Negative**

* One extra AES-GCM op per secret read. Negligible — this is a
  per-request cost, not a per-row cost, and AES-GCM is hardware-
  accelerated on every modern CPU.
* Backfill of `wrapped_lek` on pre-Phase-5 ledgers happens lazily
  at the first secret-read for each ledger (or eagerly at API
  startup in a future polish). Migration 035 leaves the columns
  NULLABLE for this window.
* The master KEK in env var is plaintext in the host's process
  environment. Same posture as ADR-0014 — graduate to a hardware-
  backed KEK when the threat model warrants.

**Doesn't replace**

* ADR-0014 Layer 1 (host disk encryption) — still required.
* ADR-0014 Layer 2 (whole-DB backup cipher) — still required for
  disaster-recovery backups (per-ledger crypto can't help when
  the master KEK is lost; Layer 2's separately-managed cipher is
  the recovery path).

## Alternatives considered

* **Per-record DEK as ADR-0014 §Layer 3 wrote it.** Cleanest for
  one-off secrets but doesn't compose with per-ledger
  export/import. Rejected as the primary path; the schema shape
  here is a superset, so per-record DEK can be reintroduced for
  records that aren't ledger-bound.
* **User-supplied per-ledger passphrase (zero-knowledge from
  operator).** Heavy friction (the user *is* the operator in a
  self-hosted single-user app), composes poorly with WebAuthn
  (no passphrase entry in the login flow), and a lost passphrase
  is irrecoverable data loss. Rejected.
* **AES-KW for the wrap step.** Cryptographically the textbook
  choice, but pulls in `BouncyCastle.Cryptography` for one
  operation. AES-GCM with a random nonce is equivalent in
  practice at this volume. Rejected on dependency cost.
* **Cache unwrapped LEK in memory across requests, keyed by
  ledger.** Marginal performance win at the cost of larger
  in-memory key footprint and harder reasoning about key
  lifetime. Phase 5 ships unwrap-per-call; revisit if the
  SimpleFIN sync path is shown to be CPU-bound on this op (it
  won't be — the bottleneck is HTTP I/O).

## Rotation (realized — ADR-0060 follow-up)

Master-KEK rotation is cheap because of the envelope structure: only the
**wrappings** change, never the bulk data. Two things are sealed directly under
the master KEK — every `ledgers.wrapped_lek`, and the backup passphrase in
`global_scheduled_jobs.passphrase_ciphertext` (ADR-0060). Everything else is
sealed under the per-ledger LEK, whose plaintext is unchanged, so it needs no
work.

`coffer-api rotate-kek` (operator CLI, `KekRotationService`) re-wraps both in a
single transaction — all-or-nothing, since a half-rotated DB (some blobs under
the old KEK, some under the new) would be unopenable — from the current key
(`COFFER_MASTER_KEK_BASE64`) to a new one (`COFFER_MASTER_KEK_NEW_BASE64`), and
stamps `ledgers.lek_kek_id` with the new id. `--dry-run` verifies every blob
opens under the current key without writing. Afterward the operator sets
`COFFER_MASTER_KEK_BASE64` to the new key (+ `COFFER_MASTER_KEK_ID`), restarts, and
**re-takes backups**: a `.cofferbak` carries the wrapped LEKs as they were at dump
time, so each backup is bound to the KEK era it was taken under. Operator runbook
in `docs/operations.md` § Rotating the master KEK.
